# UX Research สำหรับ Thai Street Designer: ทำอย่างไรให้การออกแบบถนนและทางแยก “เร็ว เห็นผล และแก้ได้ตรงจุด”

## บทสรุปผู้บริหาร

การวิจัยนี้พิจารณาเครื่องมือออกแบบถนน, junction geometry, traffic analysis, microsimulation, เกมสร้างโครงข่ายถนน และ creative tools โดยให้น้ำหนักกับ **official documentation/tutorials** เพื่อยืนยันว่า interaction ทำงานอย่างไร แล้วใช้ **independent reviews/forums** เป็นหลักฐานประกอบเรื่องความรู้สึก “ง่าย/ยาก” ของผู้ใช้ เมื่อมีข้อมูลเพียงพอ ส่วนคำกล่าวจาก vendor เช่น “เร็วขึ้น”, “ง่ายขึ้น” หรือ “ลดเวลา” ถูกถือเป็น **vendor claim ไม่ใช่หลักฐานอิสระ** โดยอัตโนมัติ

ข้อสรุปหลักคือ ปัญหาของ TSD ไม่ได้ดูเหมือน “ขาดฟีเจอร์” แต่เป็น **interaction architecture problem**: ผู้ใช้ต้องแปลงสิ่งที่คิดในภาษาวิศวกรรมจราจรให้เป็น object model ของซอฟต์แวร์, เดินทางระหว่างสองหน้าจอ, กรอก parameter ก่อนที่จะเห็นผล และยืนยันสิ่งที่ระบบสามารถ infer ได้เอง จุดนี้ตรงข้ามกับเครื่องมือที่รู้สึกเร็ว เช่น InfraWorks, Cities: Skylines II, CityEngine, SketchUp และบางส่วนของ Aimsun/SUMO ซึ่งพยายามให้ผู้ใช้ **กระทำกับสิ่งที่มองเห็น**, ให้ระบบสร้าง topology/default ให้ก่อน แล้วค่อยเปิดรายละเอียดเมื่อจำเป็น. หลักการนี้สอดคล้องกับงานคลาสสิกเรื่อง direct manipulation: visible objects, incremental/reversible actions และ immediate feedback ลดภาระการแปลคำสั่งเชิงนามธรรมเป็นผลลัพธ์บนจอ.

หลักฐานอิสระสนับสนุนภาพนี้ในเชิงคุณภาพ แต่ไม่ควรถูกตีความเป็นการสำรวจตลาดขนาดใหญ่ ตัวอย่างเช่น Capterra มีเพียง 7 reviews สำหรับ InfraWorks ณ เวลาที่ค้น แต่ reviewers หลายคนชมความเร็วในการทำ concept alternatives และ ease of use; G2 มี 42 InfraWorks reviews และกล่าวถึง ease of use/visualisation บ่อย แต่บาง review เป็น incentivized. ในทางตรงข้าม forum ของ Civil 3D มี anecdotal reports เรื่อง intersection/corridor workflow ที่ tedious และ geometry breaking; OpenRoads users ก็มี anecdotal reports เรื่อง Civil Cell/terrain interaction ที่ต้องแก้ไขเพิ่มเติม. สิ่งเหล่านี้เป็น **สัญญาณเชิงคุณภาพ ไม่ใช่การวัด prevalence**.

ข้อเสนอระดับสูงสำหรับ TSD จึงเป็น: **เปลี่ยนจาก “form-driven road database with a map” เป็น “plan-first parametric sketcher with an inspector.”** กล่าวคือ ผู้ใช้วาด/เลือก/ลากบน plan, ระบบสร้าง geometry ที่ plausible ให้ทันที, Inspector แสดงค่าที่สัมพันธ์กับ selection, ส่วน cross-section และ 3D เป็น linked views สำหรับตรวจผล ไม่ใช่ authoring mode แยกต่างหาก

ภาพรวมจากตารางทำให้เห็นความแตกต่างสำคัญสองแบบ

**เครื่องมือ analysis/simulation** เช่น Synchro, Vistro, SIDRA, Junctions, Vissim มีข้อได้เปรียบด้าน **compact data entry, defaults, templates และ generation of topology** แต่บางตัวแบกรับ terminology และ mode complexity สูง ซึ่งไม่เหมาะจะคัดลอกตรง ๆ มา TSD.

**เครื่องมือ graphical/conceptual และเกม** เช่น InfraWorks, CityEngine, Cities: Skylines II, Transport Fever 2 และ SketchUp แสดง pattern ที่เหมาะกับ TSD มากกว่า ได้แก่ snapping, direct handles, automatic intersections, replacing/upgrading in place, contextual properties และ drawing-time inference.

## Anti-patterns ที่ควรหลีกเลี่ยง

| Anti-pattern | ตัวอย่างและหลักฐาน | กฎสำหรับ TSD |
|---|---|---|
| **Expose implementation topology to the designer** | Vissim จำเป็นต้องมี conceptual distinction ระหว่าง `links` กับ `connectors` เพราะ simulation model ต้องการมัน และ connector creation มีขั้นตอนเฉพาะ. นั่นสมเหตุผลใน Vissim แต่ไม่ใช่ mental model ที่ TSD ต้องเปิดเผย. | `arm`, `port`, `link` ให้อยู่ใน internal model/debug UI; user-facing ใช้ `Road`, `Approach`, `Lane`, `Turn movement`, `Turn pocket` |
| **Separate geometry authoring into another page** | เครื่องมือที่ให้ direct in-canvas geometry เช่น InfraWorks, CityEngine และ Vehicle Tracking ทำให้ object กับ control อยู่ใกล้กัน. | Junction page แยกควรถูกยุบเป็น inspector/drawer บน workspace เดียว |
| **Ask permission for every predictable topology event** | InfraWorks สร้าง intersection จาก road crossing โดยอัตโนมัติ; SUMO/Aimsun ก็ generate network structure ก่อนแล้วให้ fine-tune. | Auto-create + Undo ดีกว่า modal “Confirm intersection?” ทุกครั้ง |
| **Wizard before visible result** | Civil 3D Intersection Wizard มีประโยชน์มากสำหรับ detailed corridor automation แต่ต้องมี prerequisite alignments/profiles และสร้าง dependent objects จำนวนมาก; forum feedback บางรายชี้ถึงความยุ่งยากในการแก้ intersection/corridor. | TSD concept design ไม่ควรบังคับ wizard หลายหน้าก่อนเห็น junction แรก |
| **Parameter wall** | Novapoint junction workflow และ analysis tools อย่าง Vistro/SIDRA สามารถรองรับ parameter จำนวนมากได้ดีในบริบท expert analysis แต่ input ยังเป็น form/table-centric. | Basic inspector ต้องแสดงเฉพาะค่าที่เปลี่ยน shape/meaning บ่อย; field อื่นอยู่ Advanced |
| **Modifier-key choreography เป็น path หลัก** | Vissim link/connector input ใช้ Ctrl + right mouse drag และ intermediate click conventions. | Shift/Alt ใช้เป็น accelerators เท่านั้น ไม่ใช่วิธีเดียวที่จะทำ operation |
| **Smart snapping ที่ผู้ใช้ override ไม่ได้** | SketchUp community มี anecdotal complaints เรื่อง inference ที่ snap ไป target ที่ไม่ต้องการ; Transport Fever users ก็มี feedback เรื่อง auto-snapping/fine placement. | ทุก snap ต้องมี visible cue, priority ที่คาดเดาได้ และ temporary disable |
| **Silent regeneration / silent failure** | InfraWorks เป็นตัวอย่างที่ดีกว่า: invalid transition ไม่ถูก apply และมี tooltip บอกเงื่อนไข; SUMO แสดง reason ของ conflict. | ถ้าการเปลี่ยน pocket/radius ทำอะไรไม่ได้ ต้องบอก “ทำไม” และชี้ geometry ที่เป็น constraint |
| **Parametric dependency ที่แกะไม่ออก** | OpenRoads Civil Cells มี rule/dependency structure สูง และ Bentley forum มี anecdotal reports ว่า terrain/cell interaction บางกรณีต้อง rebuild หรือแก้เพิ่มเติม. | TSD ควรใช้ parametrics เท่าที่สร้าง predictability; อย่าให้ child object เปลี่ยนโดยไม่มี visible cause |
| **Destroy-and-recreate to change type** | Cities II และ Transport Fever แสดง interaction ที่ดีกว่าด้วย Replace/upgrade in place. | Section change, junction→roundabout และ lane-count change ต้อง preserve alignment/metadata ที่ยังใช้ได้ |
| **Auto-generated result ที่ไม่มี escape hatch** | Aimsun generate default connections/conflicts แล้วมี Advanced Editor และ Reset; SUMO auto-generates connections แล้วให้ customize. | TSD auto-generation ต้อง editable, resettable และมี “Revert to auto” |
| **Scenario feature ที่ผู้ใช้ไม่กล้าใช้เพราะกลัว data loss** | จุดนี้มาจาก baseline TSD โดยตรง; Visum เป็น useful counterexample เพราะ comparison เป็น explicit network-variant concept. | Scenario operations ต้อง transactional: duplicate สำเร็จทั้งก้อน หรือไม่เปลี่ยนอะไรเลย; undoable และมี clear current-scenario indicator |

ข้อควรระวังสำคัญคือ **ไม่ควรเลียนแบบเกมจนสูญเสีย engineering precision**. Cities: Skylines II เป็น benchmark ที่ยอดเยี่ยมสำหรับ topology creation, Replace และ roundabout placement แต่ไม่ได้มีข้อกำหนดเดียวกับ concept engineering tool. แนวทางที่เหมาะกับ TSD คือใช้ **game-like construction speed + engineering-like explicit dimensions**: geometry เกิดเร็วเหมือนเกม แต่ width, radius, storage, taper และ offsets ยังพิมพ์ค่าจริงเป็นเมตรได้เหมือน professional tools.

## โมเดลปฏิสัมพันธ์ที่แนะนำสำหรับ TSD

แกนของโมเดลควรเป็น workspace เดียว:

**Canvas ตรงกลาง** = authoring, **Inspector ด้านขวา** = precise values, **context toolbar ใกล้ selection** = high-frequency commands, **Scenario bar ด้านบนหรือด้านล่าง** = Existing / Alt A / Alt B / Compare, และ **cross-section/3D** = linked inspection views ที่ไม่ทำให้ผู้ใช้หลุดจาก object ที่เลือก

เมื่อ selection เปลี่ยน inspector เปลี่ยนตาม:

`Road → Road section`  
`Junction → Junction type + global geometry`  
`Approach → pockets/crosswalk/stop line`  
`Pocket → storage/taper/width`  
`Roundabout → ICD/apron/approaches`  

รูปแบบนี้ยืมหลัก selection-driven properties จาก Figma และ Stack/in-canvas editing จาก InfraWorks ขณะที่แยก basic/advanced แบบ Aimsun.

เพื่อเปรียบเทียบ action count อย่างโปร่งใส ข้อเสนอนี้นับ **หนึ่ง click/tap, หนึ่ง drag gesture, หนึ่ง keyboard command หรือหนึ่ง committed field edit = หนึ่ง action**; geometry regeneration, snapping และ auto-junction ที่ระบบทำเองไม่นับเป็น user action. ดังนั้นตัวเลขเป็น design target สำหรับ benchmark ไม่ใช่ผล usability test ที่วัดแล้ว

| Workflow | Interaction ที่แนะนำ | Target actions | เทียบ baseline |
|---|---|---:|---|
| **วาดถนน 4-lane divided / เชื่อมสอง junctions** | ① เลือก preset `2+2 Divided` จาก recent preset chip; ② click/snap road end A; ③ click/snap road end B. หากต้องมี intermediate vertex ให้เพิ่มหนึ่ง action ต่อ vertex. Endpoint hit target มี magnetic halo; drawing guide แสดง length/angle; พิมพ์ length ได้โดยไม่เปิด dialog. Pattern นี้อิง InfraWorks assembly+length constraint, SketchUp precision entry และ Transport Fever snapping. | **3** | T2: **5 → 3**, ลด 40% |
| **สร้าง four-leg junction** | ผู้ใช้ลาก road ให้ตัดอีก road; **junction เกิดอัตโนมัติ ไม่ถาม confirmation**. Toast สั้น ๆ: `4-leg junction created · Undo · Keep crossing only`. ไม่มี action เพิ่มใน normal case. InfraWorks/SUMO/Aimsun สนับสนุน model ที่ topology ถูก generate ก่อนแล้วค่อยแก้ exception. | **0 เพิ่มเติม** | ปัจจุบันมี confirmation ทุก crossing → target 0 |
| **ปรับ junction** | ① click junction; ② drag corner-radius handle หรือ click dimension แล้ว type exact radius. Inspector แสดง `Type`, `Corner radius`, `Crosswalks`, `Stop lines`, `Signals`; Advanced ซ่อน detailed per-approach parameters. Dual graphical/numeric pattern มีใน Vehicle Tracking/CityEngine/InfraWorks. | **2–3** | ไม่ควรต้องเปิดหน้าอื่น |
| **เพิ่ม right-turn pocket 3.0 m / 50 m / 30 m** | เมื่อ junction selected: ① click approach หรือ movement arrow; ② `Add → Right-turn pocket`; ③ edit Width=`3.0`; ④ Storage=`50`; ⑤ Taper=`30`. Geometry preview เปลี่ยนทันที; handle สามตัวบน canvas สะท้อนค่าเดียวกับ fields. สำหรับ Thai left-hand preset pocket ถูกวางฝั่ง median โดย default แต่ user override ได้. Vistro/InfraWorks แสดง precedent สำหรับ semantic pocket/widening data และ graphical transition editing. | **5** | T1: **12 → 5**, ลดประมาณ 58% |
| **เพิ่ม Slip lane** | ① click near-side turn/approach; ② `Add Slip lane`. ระบบสร้าง island + lane ด้วย contextual default; optional ③ drag/type radius/width ถ้าต้องปรับ. Vehicle Tracking และ SIDRA treat Slip lane เป็น semantic feature แทน primitives. | **2** default / **3–4** adjusted | ปัจจุบันควรเปลี่ยนจาก field/object assembly เป็น feature command |
| **เปลี่ยน junction เป็น roundabout** | ① select junction; ② click type chip `Roundabout`; preview แสดง candidate; ③ เลือก `S/M/L` หรือ type ICD exact; optional ④ drag approach blend point. Existing approach widths/lane count ถูกใช้สร้าง initial geometry; incompatible details แสดง summary ก่อน drop เช่น `2 stop lines will be replaced by yield lines`. InfraWorks ใช้ conversion + contextual initial style; Cities II ใช้ placement บน existing intersection; Vehicle Tracking ใช้ standards + grips. | **3** typical | เป้าหมายคือ “convert”, ไม่ใช่ delete/rebuild |
| **เพิ่ม median opening / U-turn** | ① select median ใกล้ตำแหน่ง; ② `Add → Median opening / U-turn`; ③ click/drag station; ④ type opening width หรือใช้ default. Directional arrows preview movement ที่ legal ภายใน model; error บอกถ้า opening ชน pocket/transition. | **3–4** | ไม่มี baseline; ตั้ง benchmark ใหม่ |
| **เปลี่ยน section เป็น 3.5 m lanes + 2.5 m sidewalks** | ① select road; ② lane-width field `3.5`; ③ sidewalk linked field `2.5`. `Both sides linked` เป็น default; unlink เมื่อจะทำ asymmetric. Direct/symmetric width interaction มี precedent ใน CityEngine. | **3** | T3: **17 old / 5 new → 3**; ลด 40% จากหน้าปัจจุบัน |
| **สร้าง Alternative + เพิ่ม Slip lane + compare** | ① `Existing ▾ → Duplicate as Alternative`; system switches to Alt 1; ② select approach; ③ `Add Slip lane`; ④ click `Compare with Existing`. Comparison เปิด overlay หรือ split-view; unchanged muted, Added/Changed emphasized. Scenario/diff concepts มี precedent ใน Visum และ ConceptStation. | **4** | T4: **ทำไม่ได้ → 4**, พร้อม transactional safety |
| **Export plan figure** | ① `Export`; ② click retained preset `Report plan — PNG` หรือ `SVG`. Preview ไม่ควรบังคับถ้าค่าครั้งก่อนยัง valid. | **2** | T5: **2 → 2**; อย่าปรับสิ่งที่ไม่เป็นปัญหา |

เมื่อรวม benchmark เดิม ส่วนที่ควรตั้งเป็น **North-star UX metric** คือ:

| Benchmark | Baseline | Target |
|---|---:|---:|
| T1 Four-leg junction + exact right-turn pocket | 12 | **≤5–6** |
| T2 Connect junctions, 2+2 divided | 5 | **≤3** |
| T3 Set 3.5 m lanes + 2.5 m sidewalks | 17 old / 5 new | **≤3** |
| T4 Duplicate Alternative + Slip lane + compare | Failure | **100% completion; ≤4–5 actions** |
| T5 Export plan | 2 | **≤2** |

ไม่ควรพยายามลดทุกงานเหลือ click เดียว ค่า width/storage/taper ที่เป็น **explicit design intent** สมควรนับเป็น actions; สิ่งที่ควรถูกตัดออกคือ actions ที่มีไว้เพื่อ “บอก software ในสิ่งที่มันรู้อยู่แล้ว” เช่น confirm crossing, navigate ไปอีก page, เลือก internal port หรือ re-enter geometry ที่สามารถ inherit ได้.

องค์ประกอบ feedback ที่ควรเกิดบน canvas มีห้าประเภท: snap/inference cue, dimensions, preview geometry, validation state และ consequences of conversion. InfraWorks, SketchUp, SUMO และ Vehicle Tracking แสดงตัวอย่างของ feedback เหล่านี้ในรูปแบบต่างกัน.

ตัวอย่างข้อความที่เหมาะกว่า error ทั่วไป:

> **Right-turn pocket shortened to 34 m**  
> Requested 50 m overlaps the upstream lane transition.  
> `Move transition` · `Use 34 m` · `Cancel`

และสำหรับ automatic junction:

> **4-leg junction created**  
> Roads intersect at chainage 0+245.  
> `Undo` · `Keep crossing without junction`

ทั้งสองตัวอย่างเป็น **ข้อเสนอสำหรับ TSD ไม่ใช่ข้อความจากผลิตภัณฑ์ที่ศึกษา**.

## Roadmap ที่จัดลำดับตาม impact ต่อ effort

ลำดับด้านล่างตั้งใจให้ single developer สามารถสร้าง improvement ที่รู้สึกได้ก่อน โดยหลีกเลี่ยงการเริ่มจาก geometry engine rewrite ขนาดใหญ่

| ลำดับ | กลุ่ม | Improvement | เหตุผล | Effort / Impact |
|---:|---|---|---|---|
| 1 | **Quick wins — days** | **เปลี่ยน vocabulary: ซ่อน arm / port / link** | ปัญหา mental-model โดยตรง และแทบไม่ต้องเปลี่ยน geometry engine; consistency/match-to-real-world เป็น usability principle หลัก. | S / High |
| 2 | **Quick wins — days** | **ขยาย endpoint/handle hit areas + hover/snap halo** | แก้ T2 small-target friction โดยตรง;ไม่ต้องมี full snapping engine ก่อน | S / High |
| 3 | **Quick wins — days** | **Road preset chips: 2-lane, 2+2 divided, 3+3 divided** | ตัด section setup ก่อน/หลัง drawing; precedent จาก road assemblies/templates. | S / High |
| 4 | **Quick wins — days** | **remember last-used section/junction defaults** | expert repetition เร็วขึ้น; Vissim ใช้ inheritance จาก recently-created object. | S / Med–High |
| 5 | **Quick wins — days** | **Progressive disclosure ใน inspector** | แสดง Width/Storage/Taper/Radius ก่อน; Advanced ทีหลัง; Aimsun/Junctions เป็น precedent. | S / High |
| 6 | **Quick wins — days** | **Mode indicator + `Esc → Select` + cursor feedback** | ลด mode errors ก่อนเพิ่มเครื่องมือใหม่. | S / High |
| 7 | **Quick wins — days** | **Contextual validation messages แทน generic errors** | error prevention และ recovery ดีขึ้นทันที; InfraWorks/SUMO เป็น reference. | S / High |
| 8 | **Medium — weeks** | **รวม Road/Junction editing กลับสู่ workspace เดียวด้วย selection-driven Inspector** | เป็น structural fix ที่สำคัญที่สุดต่อ “two separate screens”; Figma/InfraWorks pattern. | M / Very High |
| 9 | **Medium — weeks** | **Auto-create junction at crossings + Undo / no-junction override** | ตัด confirmation ทุก crossing; precedent ชัดจาก InfraWorks/SUMO/Aimsun. | M / Very High |
| 10 | **Medium — weeks** | **Endpoint + angle + alignment snapping/inference engine** | แก้หนึ่งใน known friction หลัก; ต้องมี override และ cue. | M / Very High |
| 11 | **Medium — weeks** | **Inline road/junction dimensions + numeric editing** | ผู้ใช้สามารถลากและ type exact number โดยไม่เปิด page/dialog; InfraWorks/CityEngine/Vehicle Tracking. | M / High |
| 12 | **Medium — weeks** | **Semantic `Add right-turn pocket` / `Add Slip lane` commands พร้อม compact popover** | ตรงกับ T1/T4 และ vocabulary ของ engineer; Vistro/Vehicle Tracking/SIDRA เป็น precedent. | M / Very High |
| 13 | **Medium — weeks** | **Scenario duplicate/compare hardening + visual diff** | T4 เคยมี catastrophic failure; concept alternatives เป็น core use case. Visum ให้ useful model ของ explicit version comparison. | M / High |
| 14 | **Large — months** | **Unified parametric junction regeneration + one-click Cross/T/Roundabout conversion preserving compatible features** | ต้องจัด dependency ระหว่าง pockets, islands, crosswalks, stop lines, median และ roundabout; InfraWorks/Vehicle Tracking แสดง end-state ที่ควรไปถึง. | L / Very High |
| 15 | **Large — months** | **Station-based transitions + optional OSM/GeoJSON bootstrap** | lane-count transitions ต้อง direct-editable; import ช่วย existing-network setup แต่ไม่ควรแซง core drawing UX. InfraWorks/ConceptStation/SUMO แสดงทั้ง transition handles และ data bootstrap. | L / Med–High |

ลำดับนี้หมายความว่า **ไม่แนะนำให้เริ่มจาก 3D, photorealistic rendering, extensive template library หรือ advanced import** แม้เครื่องมืออย่าง InfraWorks, ConceptStation, Twinmotion และ Lumion จะเก่งด้านนั้น. สำหรับ TSD primary job คือ concept geometry บน plan; rendering ที่ดีไม่ชดเชย 12 actions เพื่อทำ pocket หรือการต้องเปลี่ยนหน้าจอเพื่อแก้ junction. InfraWorks reviews เองชี้ว่าความแข็งแรงของผลิตภัณฑ์ใน conceptual context อยู่ที่ speed/context/visualisation มากกว่าการเป็น detailed-design replacement.

ลำดับ implementation ที่แนะนำเป็นพิเศษคือ **อย่ารอ full snapping engine ก่อนแก้ T2**. เริ่มจาก enlarged endpoint target + snap halo ก่อน จากนั้นเพิ่ม endpoint snap → angle inference → parallel/perpendicular → length entry ตามลำดับ ซึ่งลด risk ของการสร้าง inference system ใหญ่เกินจำเป็น.

เช่นเดียวกัน **อย่ารอ junction-engine rewrite ก่อนเลิก two-screen workflow**. Inspector สามารถเป็น façade เหนือ data model ปัจจุบันก่อน แล้วค่อย migrate geometry direct-manipulation ทีละ feature วิธีนี้ให้ UX gain เร็วกว่าการ rewrite backend ทั้งก้อน.

## แผน Usability Test สำหรับ benchmark รุ่นใหม่

แนะนำทดสอบกับ traffic engineers/transport planners ที่ตรงกลุ่มเป้าหมาย โดยมีทั้งผู้ที่ไม่เคยใช้ TSD และผู้ใช้ที่คุ้นกับรุ่นปัจจุบัน เพื่อแยก **learnability** ออกจาก **expert efficiency**. งานวิจัย HCI เรื่อง complex applications พบว่าผู้ใช้มักพยายามเรียนด้วย trial-and-error มากกว่าพึ่ง documentation ดังนั้น test รอบแรกควรให้ผู้ใช้ลองโดยไม่มี walkthrough ก่อน แล้วจึงอนุญาต Help เมื่อผู้ใช้ต้องการ.

ไม่ควรวัดแต่ “ชอบหรือไม่ชอบ”; ควร capture interaction log เพราะปัญหาหลายอย่างของ TSD มีลักษณะ objective เช่น action count, misclick, mode error และ navigation switch.

| Benchmark task | สิ่งที่ให้ผู้ใช้ทำ | Primary measures | Target หลัง redesign |
|---|---|---|---|
| **Road creation** | เชื่อมจุดสองจุดด้วยถนน `2+2 divided`, 3.5 m lanes, median ตาม preset | completion, actions, time, endpoint misclicks, number of property panels/screens visited | ≥90% unassisted completion; **≤3 actions** ถ้าใช้ preset default, ไม่มี miss จาก target เล็ก |
| **Junction + pocket** | สร้าง four-leg junction แล้วเพิ่ม right-turn pocket 3.0 m / 50 m / 30 m | actions, time, wrong-approach selections, terminology questions, undo, exact-value accuracy | **≤5–6 actions** หลัง junction เกิด; ค่าทั้งสามถูกต้อง; ไม่มี navigation ไป separate page |
| **Section edit** | เปลี่ยน existing road เป็น 3.5 m lanes + 2.5 m sidewalks ทั้งสองฝั่ง | actions, time, symmetric-edit errors, whether user discovers linked-side behavior | **≤3 actions** จาก road selection state; ไม่มี side mismatch |
| **Junction conversion** | เปลี่ยน four-leg junction เป็น roundabout แล้วปรับ ICD/size | task success, data unexpectedly lost, number of corrections, comprehension of preview | typical **≤3 actions**; user ระบุได้ก่อน commit ว่าอะไรจะถูก preserve/replace |
| **Median opening / U-turn + conflict recovery** | เพิ่ม U-turn ใกล้ lane transition โดย intentionally ให้ตำแหน่งแรก conflict | whether user understands failure reason, time-to-recover, undo count, wrong workaround attempts | ทุกคนอธิบาย constraint ได้จาก UI โดยไม่เปิด Help; recovery ≤2 corrective actions หลัง warning |
| **Alternative workflow** | Duplicate Existing → add Slip lane → Compare | completion, scenario confusion, accidental edits to Existing, data loss, actions | **100% data integrity**, **≤4–5 actions**; ไม่มี participant แก้ Existing โดยไม่ตั้งใจ |
| **Report output** | export Existing/Proposed plan figure เป็น PNG หรือ SVG สำหรับ report | actions, wrong-scenario export, need to reposition/clean UI artifacts, output legibility | **≤2 actions** หลัง framing พร้อม; export ระบุ scenario ชัด |

ทุก task ควรบันทึกอย่างน้อย:

**Task success**, elapsed time, user actions, misclicks, undo/redo count, failed commands, mode changes, visits to Help, number of timesผู้ใช้เปิด/ปิด inspector และจำนวนครั้งที่สลับ workspace/page. หลังแต่ละ task ให้ตอบคำถามเดียว “งานนี้ง่ายหรือยากเพียงใด?” แบบ 1–7 และจดคำอธิบายสั้น ๆ; คะแนนนี้ควรใช้คู่กับ behavioral metrics ไม่ใช่แทนที่ metrics เหล่านั้น.

สำหรับ TSD โดยเฉพาะควรเพิ่ม telemetry events ที่ไม่เก็บเนื้อหางานเกินจำเป็น เช่น:

`road_draw_started → snap_used → road_completed`  
`junction_auto_created → undo_junction / keep_junction`  
`pocket_added → pocket_parameter_changed → validation_error`  
`scenario_duplicated → compare_opened`

สิ่งที่ต้องสังเกตเชิงคุณภาพมากที่สุดไม่ใช่เพียง “ผู้ใช้ทำสำเร็จหรือไม่” แต่คือ **ช่วงเวลาที่ผู้ใช้หยุดและถามตัวเองว่า object ไหนต้องเลือก**. ถ้าผู้ทดสอบพูดว่า “ต้องเลือก arm หรือ road?”, “port นี้คืออะไร?”, “แก้ฝั่งไหน?” หรือ “ต้องเข้า junction page ไหม?” นั่นเป็นหลักฐานว่าระบบยังบังคับผู้ใช้คิดใน data model ของ TSD แทนที่จะคิดใน model ของวิศวกรจราจร.

เกณฑ์การตัดสิน redesign หลังสองรอบทดสอบควรให้น้ำหนักตามลำดับนี้: **task completion และ data integrity ก่อน, action/time ต่อมา, subjective ease หลังจากนั้น**. เป้าหมายไม่ใช่ทำให้ TSD มีฟีเจอร์เท่า Civil 3D, InfraWorks, Vissim หรือ SIDRA แต่ทำให้ workflow ที่อยู่ในขอบเขตของ TSD—**sketch road → form junction → adjust concept geometry → branch Alternative → compare → export**—ใช้ภาษาของ traffic engineer, เกิดขึ้นบน plan เดียว, และให้ผลลัพธ์ที่เห็นและย้อนกลับได้ทุกขั้น. หลักฐานจาก direct-manipulation research, professional concept tools, network editors และ road-building games ชี้ไปในทิศทางเดียวกันว่า **software รู้สึกง่ายเมื่อระบบรับผิดชอบ topology/defaults ส่วนผู้ใช้รับผิดชอบ design intent**.
