# Canonical alignment and explicit station migration

## Compatibility decision

Opening an existing RoadFirst schema-1 project keeps its original compile behaviour. It is not automatically converted. Network imports retain the same legacy path. New projects use schema 2 and new roads carry `alignment: 'arc'`. A schema-2 project can retain unmigrated roads; absence of the flag always means the original chord-station convention.

The project inspector offers **ตรวจการแปลงแนวโค้ง**. Preview shows before/after road reference lines and crossing locations, length changes, PVI/opening counts, dormant decisions, newly found crossings and blockers. Confirm applies to the active scenario only, through a single undoable command. Cancel changes nothing. Save/reopen preserves the chosen convention. Diamond origin version 1 and its parameters remain unchanged; no template generator is called.

## One resolved alignment

`core/common/resolved-alignment.ts` owns finite lines and circular arcs, analytic arc lengths, point/tangent queries, nearest projection and line/arc intersections. Fillet fit uses the existing tool geometry, not an engineering standard. The former 200 m interaction cap stays for legacy editing; converted/new roads use the actual available tangent geometry. The 10,000,000 upper bound is a serialization/data bound, not a design criterion or starting value.

The road compiler passes a derived alignment slice into each Network link. Plan, section, 3D and export obtain their linework from that same slice. Tessellation has a maximum 0.001 m chord error; sampled points retain exact arc-length station metadata. Snap, anchors and road-opening handles query the analytic alignment. Legacy Network link generation is unchanged.

## Migration contract

- Map old control-polyline stations monotonically through tangent boundaries and arc midpoints. Preserve every authored PVI and its z. Map both opening ends, not only its start.
- Process anchor hosts before attached ramps. Move attached endpoints using the host's resolved point/tangent and retain the traffic side. Cyclic dependencies block conversion.
- Keep decisions with no remaining crossing dormant, with all treatments. Leave newly detected crossings unresolved. Ambiguous multiple crossing matches block conversion instead of guessing.
- Map link-local components and transition bounds against the old compiled link and new alignment. Changed link counts, out-of-range data and reversed ranges block conversion. No component is discarded.
- Preserve scenarios independently. Preview and refused confirmation never mutate the source project.

## Supported boundary

The existing junction engine has straight approaches. A curved new/converted alignment that cannot provide enough straight approach length must be adjusted before it can form a junction. Commands and migration reject such a junction with an explanation; grade-separated crossings on arcs remain supported. This PR does not implement a curved junction-arm engine.

Joining converted roads with PVI, anchors, template origin or link settings is refused until these records can all be transferred losslessly. It must not inherit the older join operation's data-dropping behaviour. Joining plain converted roads is supported. Mixing old/new station conventions in a join requires conversion first.

Ramp terminal/gore/lane geometry remains the existing draft and is not completed here. No new engineering default or verified standard is introduced.
